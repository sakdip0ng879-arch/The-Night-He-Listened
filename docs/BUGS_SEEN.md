## หมวด A — ตัวตรวจจับได้ (ถ้ารันจริง)

### A1 · `clash` + `mapDelta` ของเมืองเดียวกัน ในฉากเดียวกัน = ผิด
engine สะสม delta ก่อนวาด **เจ้าของเปลี่ยนไปแล้วตอนวงปะทะถูกวาด** ภาพจึงกลายเป็น
ฝ่ายชนะบุกตีแผ่นดินตัวเอง
→ เมืองที่ "แตก" ไม่ใช่ "ถูกตี" ให้ใช้ `pin` แทน `clash` · `check_map` จับให้

### A2 · ลูกศรออกจากแผ่นดินข้าศึก
`check_map` ข้อ 5 · error เว้นแต่ฉากมีการปะทะ (กำลังล้อมเมืองอยู่) หรือ `retreat:true`
→ DECISIONS §6

### A3 · กล้องแคบเกิน 520
ยิ่งแคบยิ่งไม่มีหมุดหลุด **ตัวตรวจรุ่นเก่าจึงเงียบสนิทในเคสที่แย่ที่สุด**
ตัวอักษรที่พิมพ์มากับแผนที่บวมจนบดกันเอง และเส้นทางเดินทัพเหลือแค่เศษเส้น
→ `check_camera` ตรวจ `TIGHT = 520` แล้ว · DECISIONS §5

### A4 · เลขบนป้ายเกินกำลังพลที่ฝ่ายนั้นมี
`check_hud` ตาราง `CLAIMS` · เพิ่มฉากที่เอ่ยจำนวนทัพเมื่อไหร่ ต้องเพิ่มลงตารางด้วย

### A5 · ★ landmask ทำเครื่องหมายแม่น้ำเป็น "น้ำ" และเมืองโบราณตั้งอยู่ริมแม่น้ำ
**เจอ 2026-08-25 ตอนรัน `check_routes` รอบแรกของโปรเจกต์นี้**

`landmask.js` เป็นตาราง 330×390 ที่ **1 ช่อง = 5 หน่วยบนแผนที่** และมันไม่ได้แยกทะเลกับแม่น้ำ
ตัวตรวจรุ่นแรกของผมเขียนว่า *"จุดต้องอยู่บนบก"* ตรง ๆ แล้วมันฟ้อง **ภูมิศาสตร์ที่ถูกต้อง** ทันที 5 จุด
— Langzhong · Jieting · Xiegu · Ji Cheng · Wu Gong — ทั้งที่ทุกพิกัดสอบเทียบมาแล้วสองโปรเจกต์

วัดจริงในรัศมี 15 หน่วยรอบจุด:

| จุด | ช่องที่เป็นน้ำ |
|---|---|
| Ji Cheng | 22/49 |
| Xiegu | 21/49 |
| Langzhong · Jieting | 11/49 |
| Tianshui | 8/49 |
| **Chang'an** | **2/49** |

แม้แต่ Chang'an ก็ยังมีน้ำอยู่ข้าง ๆ · **เมืองตั้งริมน้ำเพราะคนต้องกินน้ำ** ไม่ใช่เพราะพิกัดผิด

**กฎที่ถูก** — "อยู่บนช่องน้ำ" ไม่ใช่ความผิด สิ่งที่ผิดคือ
- **จุด**: ลอยอยู่*กลางผืนน้ำ* (รอบตัวรัศมี 15 หน่วยเปียกเกิน 7 ใน 8 ทิศ)
- **เส้นทาง**: **ความยาวของช่วงที่เปียกติดต่อกัน** เกิน 30 หน่วย ≈ 6 ช่อง ซึ่งกว้างกว่าแม่น้ำ
  สายไหนบนแผ่นนี้ · ถนนที่เลาะหุบเขาแม่น้ำแตะน้ำเป็นระยะ 7–15 หน่วย ซึ่งถูกต้อง

**ยืนยันว่าตัวตรวจยังจับได้จริง** (ตามหมวด C4) ด้วยการใส่บั๊กกลับเข้าไปสองแบบ —
ถนนตรงจาก Chengdu ไป Jianye จับได้ที่ 36 หน่วย · จุดที่วางกลางทะเลจับได้เช่นกัน

## หมวด B — ★ ต้องถ่ายภาพเท่านั้นถึงจะเจอ

> **ทั้งหมวดนี้ผ่านตัวตรวจทุกตัวได้สบาย** เพราะ DOM ถูกต้องหมด ผิดตอนเรนเดอร์เท่านั้น
> นี่คือเหตุผลที่ DECISIONS §13 บังคับให้ถ่ายภาพก่อนปิดงานทุกครั้ง

### B1 · ★★ ลูกศรวิ่ง route จนสุดเสมอ — มันจึงพูดว่า "ไปถึงแล้ว" ทุกครั้ง
**ทุ่นระเบิดที่ใหญ่ที่สุดของทั้งชุด** engine ลาก `d` ทั้งเส้นเสมอ ไม่มีทางให้หยุดกลางทาง
การไล่ตามที่ไล่ไม่ทัน วาดเป็นลูกศรไม่ได้ — มันจะอ่านเป็น "บุกถึงปลายทางแล้ว"

**เกณฑ์: ถ้าฝ่ายนั้นไม่ได้ไปถึงปลายทาง อย่าใช้ลูกศร ใช้หมุดที่มี `side`**

⚠ **โปรเจกต์นี้จะเจอข้อนี้บ่อยกว่าสองโปรเจกต์ก่อนมาก** เพราะเรื่องเต็มไปด้วยการทัพที่
ไปไม่ถึง — Cao Zhen 224 หยุดกลางทาง · Sima Yi สี่ครั้งปี 236–241 ถอยทุกครั้ง ·
Cao Shuang 244 ไม่พ้นชะง่อน · ทัพม้าฮั่นที่ไปช่วยเผ่า Qiang **ไปถึงช้าไปสิบเอ็ดวัน**
**ฉากพวกนี้ทั้งหมดต้องเป็นหมุด ไม่ใช่ลูกศร**

### B2 · ★ ลูกศรสองอันบน route เดียวกัน = อันหลังลบอันแรกทิ้ง
`.mk-route.retreat` เปลี่ยนแค่ opacity ไม่ได้ทำเป็นเส้นประ (ลายประถูก `strokeDasharray = L`
ของอนิเมชันทับไปแล้ว) · ถ้าวาดสองอันบน `d` เดียวกันทิศเดียวกัน อันหลังทาทับจนหายสนิท
→ ให้ถนนเส้นนั้นเป็น **วงปะทะ** แทนลูกศรที่สอง
**ห้ามแก้ด้วยการสร้าง route ปลอมให้เยื้องกัน** (§D1)

### B3 · วงปะทะสองอันที่ห่างกัน < ~40 หน่วย พันกันเป็นก้อนเดียว
Mei (516,663) กับ Wuzhang (503,661) ห่างกัน **13 หน่วย** ซูมเท่าไรก็ไม่แยก
→ เหลือวงเดียว แล้วให้ร้อยแก้วเล่าอีกศึก
⚠ โปรเจกต์นี้ใช้ Mei กับ Wuzhang ติดกันหลายฉากในภาคเจ็ด **จะเจอแน่**

### B4 · `setAttribute('fill', …)` แพ้กฎใน CSS เสมอ
`.mk-halo{fill:var(--gold)}` กับ `.mk-dot{fill:var(--gold)}` ชนะ presentation attribute
หมุดที่มี `side` จึงเป็นทองหมดอยู่หลายเดือนโดยไม่มีใครรู้
→ ใช้ `.style.fill` (inline style ชนะ CSS class) · **แก้แล้วใน `strategic.js` ของโปรเจกต์นี้**

### B5 · แถบเวลาล้นทับตัวนับ และมันกิน "ฉากท้ายเล่ม" ก่อนเพื่อน
`.tcell` เป็น `<button>` เบราว์เซอร์ใส่ padding ปริยาย ~6px สองข้าง = 12px ต่อช่อง
วัดจริงที่ 61 ฉาก จอ 1904: `#track` กว้าง **1534px ในกล่อง 1398px** ล้นขวา 136px
ช่องสุดท้ายไปจบนอกจอ กดไม่ได้ มองไม่เห็น

**อาการที่หลอกตา:** ภาพอ่านได้ว่า `"8 / 61"` เพราะเลข 5 ถูกช่องสีทองทับพอดี —
**วินิจฉัยผิดไปหนึ่งรอบ** ว่าเป็น race ใน `shot.ps1` ตัวที่ชี้ขาดคือ crop ภาพที่ 6x

→ `padding:0` ต้องอยู่ใน `.tcell` ฐาน ไม่ใช่แค่ใน `@media (max-width:700px)` · **ตรวจแล้วว่าติดมา**
⚠ **ข้อนี้โตตามจำนวนฉาก และกินจากท้ายแถบเสมอ** เรื่องนี้ยาว 11 ภาค จะมีฉากมากกว่าทั้งสองเล่มก่อน
**ทุกครั้งที่ปิดบท ให้ดูมุมขวาล่างของภาพสักใบ**

### B6 · หัวลูกศรที่ไปจบใต้วงปะทะพอดี จะถูกบังจนดูไม่ออก
→ ลากเส้นจบก่อนถึงวงปะทะ

## หมวด C — เครื่องมือหลอก

### C1 · ★ `build_timeline` ไม่เขียนไฟล์เมื่อมี error และ PowerShell ตัด output ทิ้ง
เรียกแบบ `| Select-Object -First 1` → PowerShell หยุด pipeline ทันทีที่ได้ครบจำนวน
บรรทัด `✖ ผิด N รายการ` กับ `✔ เขียนไฟล์แล้ว` อยู่ท้ายสุดทั้งคู่ จึงไม่ถูกพิมพ์
**ผลคือเห็นแต่ "beat ทั้งหมด: N" แล้วนึกว่าผ่าน ทั้งที่ไฟล์ไม่ได้ถูกเขียน**
แล้วตัวตรวจตัวถัดไปอ่าน `timeline.js` เก่า แล้วรายงานว่าผ่านหมด

→ **เรียก `build_timeline` แบบไม่ตัด output เสมอ** (หรือเก็บใส่ตัวแปรก่อนค่อยกรอง)

### C2 · ห้ามเปิดผ่าน `file://` เพื่อตรวจงาน
preview pane แคชไว้ · แก้ข้อมูลแล้วหน้าไม่เปลี่ยน จะตรวจผ่านทั้งที่ของจริงพัง
→ `shot.ps1` เปิดผ่าน http ให้อยู่แล้ว ใช้อันนั้น

### C3 · ห้ามเขียนเครื่องมือตรวจที่ "จำลอง" การเรนเดอร์ขึ้นมาใหม่
โปรเจกต์ 1 เคยเขียน `render_battle.ps1` วาดด้วย GDI+ เพื่อตรวจการจัดวาง — มันตรวจผ่าน
ในขณะที่ของจริงพัง เพราะมันไม่ได้วาดสิ่งเดียวกับที่เบราว์เซอร์วาด

### C4 · ตัวตรวจที่รายงาน "ไม่เจออะไร" อาจแปลว่ามันพัง
รอบแรกของ `selfcheck` เขียนผิดเอง 2 จุด — `getBBox` คืนกรอบ **ก่อน** transform ทำให้ทุกหน่วย
กองอยู่ที่ (0,0), และดักทุก path ที่ระบายสีทั้งที่ชั้นพื้นที่ยึดครองต้องระบายอยู่แล้ว
→ **ต้องจงใจใส่บั๊กกลับเข้าไปเพื่อพิสูจน์ว่าตัวตรวจจับได้จริง**

### C5 · บั๊กบางตัวโผล่เฉพาะตอนเปลี่ยนฉากติด ๆ กัน
`shot.ps1 next:7` กดปุ่มจริง 7 ครั้ง — จับบั๊กกล้องกระเด็น (`ease(t)` ระเบิดตอน t ติดลบ)
ได้ ทั้งที่ตรวจแบบ "กระโดดไปทีละฉาก" ผ่านหมดทุกฉาก

## หมวด D — ข้อมูลที่เงียบ

### D1 · ★★ ห้ามแก้ปัญหา "การวาด" ด้วยการทำให้ "ข้อมูล" โกหก
โปรเจกต์ 2 พลาดข้อนี้สองครั้งในรอบเดียว สร้างเส้นทางปลอมเพื่อให้รูปไม่ทับกัน
ผลคือแผนที่บอกว่าแม่ทัพเดินไปหยุดกลางทาง ทั้งที่เรื่องบอกว่าเขาลงมาถึงวงล้อม

**เจ้าของบอกชัดว่ารูปทับกันไม่เป็นปัญหา** — *"มันมีการย้ำตรงนั้นอยู่แล้ว คนอ่านเห็นแล้วเข้าใจทันที"*

### D2 · ★ คีย์ที่ engine ไม่รู้จัก จะไม่ error มันจะเงียบ
engine รู้จัก marker แค่ **สามชนิด**: `pin` · `arrow` · `clash`
โปรเจกต์ 2 เขียน `siege` ไว้สี่ที่และ `overlay` อีกหนึ่งที่ — **ทั้งสองไม่มีอยู่จริง**
เขียนไปไม่ error ไม่วาดอะไรเลย · โปรเจกต์ 1 เจอแบบเดียวกันกับ `{u:"…", siege:"…"}`
ที่ `applyPhase` เลือกสาขาจาก "มี `u` ไหม" ทำให้วงล้อมของ `chencang229` ไม่เคยขึ้นเลย

→ **วงล้อม** = `clash` ถ้ามีรบจริง · `pin` + `label` ถ้าเมืองเปิดเอง
→ **เส้นแบ่งบนกระดาษ** = หมุดหลายอันที่มี `side`

### D3 · รูปสัญลักษณ์ต้องมีอยู่ทั้งสองที่
ประทุนเกวียนเคยมีแค่ในโหมดสมรภูมิ พอเอามาใช้บนแผนที่ใหญ่ครั้งแรก มันตกไปเข้า `default`
ซึ่งคือสี่เหลี่ยม = ทหารราบ **โดยไม่มีอะไรเตือน**
→ จะใช้รูปใหม่ ต้องเพิ่มลงตาราง DECISIONS §3 ก่อน ห้ามยืมรูปที่มีความหมายอยู่แล้ว

### D4 · ★ ย้ายลำดับ beat แล้วต้องย้าย "สถานที่" ตามไปด้วย
เรียงตามปฏิทินอย่างเดียวไม่พอ · โปรเจกต์ 2 ปักหมุดสองฉากไว้ที่หุบเขาเป่า–เสีย ตามที่
*ต้นฉบับเล่าติดกัน* แต่พอเรียงตามปฏิทินแล้วมีฉากถอนทัพคั่นอยู่ — **หุบเขาว่างไปแล้วสามเดือน**
เจ้าของอ่านรวดเดียวแล้วถามทันทีว่าทำไมยังมีคนอยู่ตรงนั้นได้

→ **ทุกครั้งที่ย้าย beat ให้ถามว่า ณ วันที่ใหม่ คนในฉากยืนอยู่ตรงไหน ไม่ใช่ตรงไหนตอนถูกเล่า**

⚠ โปรเจกต์นี้มีภาคสามกับภาคสี่ที่เล่าซ้อนเวลากันโดยตั้งใจ **ข้อนี้จะกัดแรงกว่าเดิม**

### D5 · ต้นฉบับเล่าตาม "ลำดับเรื่อง" ไม่ใช่ "ลำดับเวลา"
เจอมาแล้วสามครั้งในโปรเจกต์ 2 → เรียงตามปฏิทินเสมอ id คงเดิม เปลี่ยนแค่ตำแหน่งใน array
ไม่งั้นแถบเวลาจะวิ่งถอยหลัง ซึ่งอ่านเป็น "แถบเวลาพัง"

### D6 · ฤดู — ระบุเฉพาะที่ต้นฉบับระบุ
การเติมฤดูให้ครบทุกฉากคือการกุความละเอียดที่ต้นฉบับไม่มี
เดือนจันทรคติ 1–3 = 春 · 4–6 = 夏 · 7–9 = 秋 · 10–12 = 冬

### E1 · ★ ต่อ path หลายช่วงโดยแทน `M` ด้วย `L` แล้วพังเงียบ

### E7 · ★★ กลุ่ม SVG ที่ถูกสลับ opacity แบบ inline **หายทั้งชั้น** จากภาพใต้ virtual time
**เจอ 2026-08-25 ตอนทำวงเส้นประ (DECISIONS §17)** — วงมีครบใน DOM (26 path · opacity 1 ·
computed style ถูกทุกค่า) แต่ภาพจาก `shot.ps1` ไม่มีสักเส้น สแกนพิกเซลทองบนแผนที่ได้ **ศูนย์**

วินิจฉัยด้วยการแยกตัวแปร: เส้นทดสอบ inline ล้วนใส่ `#L-focus` → หาย ·
เส้นเดียวกันใส่ `#L-markers` → โผล่ · **path ตัวเดิมเป๊ะ ย้ายกลุ่มแล้วโผล่ทันที**
→ ตัวที่พังคือ *กลุ่ม* ไม่ใช่เส้น: `<g>` ที่ถูกสลับ `style.opacity` 0↔1 ระหว่างโหลด
(กลไกซ่อนป้ายตอนกล้องบินของ `settleLabels`) จะไม่ถูก composite ลงภาพใต้
`--virtual-time-budget` แม้สถานะสุดท้ายจะเป็น 1 แล้วก็ตาม — **DOM บอกครบ ภาพไม่วาด**

→ แก้ใน freeze ของ `shot.ps1`: `#L-labels,#L-pins,#L-focus{opacity:1 !important}`
  (stylesheet ชนะ inline การสลับจึงเป็นโมฆะ แล้วชั้นกลับมาวาดปกติ · ไม่ใช่การโกงภาพ
  เพราะสถานะจริงตอนนิ่งของทั้งสามชั้นคือ 1 อยู่แล้ว)
⚠ **สองบทเรียนซ้อน:** (1) `#L-labels`/`#L-pins` ใช้กลไก opacity เดียวกันมาตลอด —
ภาพตรวจงานเก่าอาจไม่เคยมีป้าย/หมุดของสองชั้นนั้นเลยโดยไม่มีใครสังเกต
(2) ตัวตรวจภาพที่ "ไม่เห็นอะไร" ต้องพิสูจน์ด้วยการฉีดของที่ต้องเห็นแน่ ๆ เข้าไป (หมวด C4)

### E8 · ★ `test_roads.html` "ผ่านเงียบ" มาทั้งยุค — เพราะลืมโหลด places.js
**เจอ 2026-08-25 ตอนแก้ builder เส้นทาง** — หน้าเทสต์โหลดแค่ `roads.js` ซึ่งตั้งแต่กฎ

⚠ บทเรียนเดียวกับ C4 อีกรอบ: หน้าเทสต์ที่ไม่มีแถวผลลัพธ์ = ต้องสงสัยว่าตัวมันเองตาย

### E11 · ★ ตัวตรวจที่ "ผ่าน" เพราะคีย์ดัชนีคนละแบบ — เจอตอนยัดบั๊กทดสอบ
**2026-08-26 · ตอนเขียนข้อ 11 ของ `check_routes` (edge ที่ฉากใช้ต้องลาก d แล้ว)**

เขียนเสร็จ รันแล้วขึ้น ✔ ดูดีทุกอย่าง · แต่พอ **จงใจถอด `d` ของ wudu–xiabian ออก
แล้วรันซ้ำ มันก็ยังขึ้น ✔** — ตัวตรวจไม่ได้ตรวจอะไรเลยตั้งแต่แรก

เหตุ: `TK.edgeIndex` ที่ `roads.js` สร้างไว้ ใช้คีย์ **คั่นด้วย NUL** (`a + '\0' + b`)

ทุกการค้นจึงคืน `undefined` แล้วโค้ด `if (e && !e.d)` ก็ข้ามไปเงียบ ๆ ทุกท่อน

→ สร้างดัชนีของตัวเองจาก `TK.edges` ในบล็อกนั้นเลย ไม่พึ่งดัชนีข้ามไฟล์ ·
และเพิ่มกิ่ง `if (!e) bad(...)` ไว้ด้วย — "หาไม่เจอ" ต้องดังเสมอ ห้ามเงียบ
⚠ บทเรียนที่ต้องจำมากกว่าตัวบั๊ก: **ถ้าไม่ได้ยัดบั๊กเข้าไปทดสอบ เราจะส่งตัวตรวจ
ที่ผ่านทุกอย่างเพราะมันไม่ได้ตรวจอะไรเลย** (C4 ข้อเดิม · รอบนี้เกิดกับตัวตรวจที่เพิ่งเขียน
เพื่ออุดช่องโหว่พอดี — ตัวอุดช่องโหว่ที่รั่วเอง)

### E12 · ★★ ข้อ 8 ของ `check_routes` (ขบวนเสบียง) "ผ่าน" มาตลอดเพราะบั๊กเดียวกับ §E11

### E13 · ★★ `label` บนหมุด `clash` ไม่เคยถูกวาดลงจอเลยสักฉากเดียว
**2026-08-27 · เจอตอนดูภาพจริงของ c8-06 (ห้ากองม้าเบา) — วงปะทะสี่วงไม่มีป้ายสักวง**

ทุกฉากรบตั้งแต่บทที่ 2 เขียน `{ type:"clash", place:"...", label:"..." }` มาตลอด
และ **`label` ตัวนั้นไม่เคยไปถึงจอ** · โค้ดที่วาด clash (`js/strategic.js` ~บรรทัด 813)
สร้างแค่วงกลมสองวงกับกากบาท แล้วเรียก `forceLabels.add(m.place)` ซึ่งบังคับให้
**ชื่อเมืองที่พิมพ์อยู่บนแผ่นจริง** โผล่ขึ้นมาแทน — ไม่มีบรรทัดไหนอ่าน `m.label` เลย

**นี่ไม่ใช่บั๊ก มันคือการตัดสินใจ** และคอมเมนต์ยาวเหนือโค้ดก้อนนั้นอธิบายไว้เอง:
ราคาของศึกถูกเล่าสามที่อยู่แล้ว (ร้อยแก้ว · หลอด HUD · คอลัมน์นิยาย `.chg`)
การเอาป้ายที่สี่ไปแปะบนแผนที่ทำให้แผนที่รกโดยไม่ได้ข้อมูลเพิ่ม · และเคยลอง
"วงหนาตามราคาศึก" แล้วถอยออกมาแล้วเหมือนกัน

**สิ่งที่เป็นปัญหาจริงคือความเข้าใจผิดของคนเขียนฉาก** — ผมเขียน c8-06 โดยตั้งใจให้
วงปะทะสี่วงมีป้าย "กองที่หนึ่ง…กองที่สี่" เพื่อให้คนอ่านแมปร้อยแก้วเข้ากับภาพได้
แล้วภาพจริงออกมาเป็นวงเปล่าสี่วงที่แยกไม่ออกว่าวงไหนคือกองไหน
(รอดมาได้เพราะร้อยแก้วบรรยายเส้นทางของแต่ละกองแยกกันอยู่แล้ว — เหนือ/ถนนหลงกวาน/
หุบเว่ย/ฉีซาน ซึ่งอ่านคู่กับภาพแล้วแมปได้ตามภูมิศาสตร์)

**กติกาที่ต้องจำ:**
- `label` บน `clash` = **เอกสารในซอร์สเท่านั้น** (มีประโยชน์อยู่ ไม่ต้องถอดออก
  ทุกฉากเขียนไว้เหมือนกันหมด และมันบอกคนอ่านโค้ดว่าวงนั้นคือศึกอะไร)
- ข้อมูลที่ **คนอ่านต้องเห็น** ต้องไปอยู่บน `pin` (มี label จริง) · `strength` บนลูกศร
  (ต้องมี `who`/`name` ด้วย ไม่งั้น engine ไม่วาดชิป — ดู DECISIONS §9) · หรือร้อยแก้ว
- ⚠ **ตัวตรวจมองไม่เห็นข้อนี้** — `check_camera` นับ label ของ clash เป็นป้ายที่ต้องจัดที่ให้
  หรือเปล่าก็ไม่ทราบ แต่ที่แน่ ๆ คือมันไม่ฟ้องว่า "ป้ายนี้จะไม่ถูกวาด"
  วิธีเดียวที่จับได้คือ **ดูภาพจริง** (DECISIONS §13 อีกครั้ง)

### E14 · ★ `**ตัวหนา**` ในหมายเหตุจริง/แต่ง แสดงเป็นดอกจันจริง ๆ มาตลอด 30 ฉาก
**2026-08-28 · เจอตอนอ่านภาพจริงของ c9-06 แล้วเห็นดอกจันในคอลัมน์นิยาย**

เราเขียน `factNote` ด้วยไวยากรณ์ markdown มาตั้งแต่บทที่ 4 เพราะมันอ่านง่ายในซอร์ส
และ **ไม่มีใครเคยกดชิป "จริง/แต่ง/ผสม" ดูตอนตรวจภาพ** — กล่อง `.fnote` เป็น
`max-height:0` จนกว่าจะคลิก ภาพตรวจงานทุกใบจึงไม่เคยแสดงมันเลยสักใบ

**แก้ที่ตัวเรนเดอร์ ไม่ใช่ที่ข้อมูล** — `mdBold()` ใน `ui.js` แปลง `**x**` เป็น `<strong>`
(escape `<` `>` ก่อนเผื่อไว้) · ดีกว่าไล่ลบดอกจันใน 5 บทที่ล็อกไปแล้ว และดอกจัน
ในซอร์สมีประโยชน์กับคนอ่านไฟล์จริง ๆ

⚠ **ใช้กับ `factNote` เท่านั้น** — `text` เป็นร้อยแก้วนิยาย ไม่ควรมีตัวหนา ·
เจอ `**` หลุดเข้าไปใน `text` ของ c9-06 หนึ่งจุด (เขียนพลาดเอง) ลบทิ้งแล้ว
สแกนทั้งเล่มยืนยันไม่มีที่อื่น:

```bash
node -e "global.window={};require('./data/timeline.js');console.log(window.TK.timeline.filter(b=>b.text.includes('**')).map(b=>b.id))"
```

⚠ **บทเรียนใหญ่กว่านั้น: อะไรที่ภาพตรวจงานไม่เคยเปิด = อะไรที่ไม่เคยถูกตรวจ**
กล่องที่ต้องคลิกถึงจะเห็น · โหมดที่ต้องกดปุ่ม · สถานะที่เกิดหลังแอนิเมชันจบ —
ทั้งสามอย่างนี้อยู่นอกสายตาของ `shot.ps1` โดยสิ้นเชิง (ข้อสามคือ §E13/DECISIONS §7)

### E15 · `check_camera` ตรวจ "หัวลูกศร" แต่ไม่เคยตรวจ "หางลูกศร" (2026-09-01)

**อาการ:** ตัวตรวจรายงานเขียวทุกฉาก แต่เจ้าของดูภาพจริงแล้วบอกว่า **"มันเห็นไม่หมด"**
สามฉากรวด (c10-04 · c10-06 · c10-08) ลูกศรโผล่จากมุมจอโดยไม่มีเมืองต้นทางอยู่ในเฟรม —
ลั่วหยางหลุดกรอบ 99 และ 129 หน่วย · ฉางอานหลุด 57 หน่วย

**สาเหตุ:** `routeEnds()` คืนค่ามาครบทั้ง `start` / `end` / `mid` แต่ลูปเก็บใส่ `pts`
แค่สองตัวหลัง — **หัวกับกลาง ไม่เคยมีหาง** · บั๊กอยู่ในสิ่งที่ตัวตรวจ*ไม่ได้ทำ*
จึงไม่มีทางเห็นจากผลลัพธ์ของมันเอง มันดูสมบูรณ์แบบอยู่ทุกวัน

**ทำไมมันสำคัญกว่าที่ดู:** ลูกศรคือประโยค **"จาก A ไป B"**
ตัดหางทิ้ง = ตัดคำว่า "จาก" ทิ้ง · ฉาก c10-08 ทั้งฉากคือประโยค *"สองหมื่นห้าพันคน
เดินจากตะวันตกมาตะวันออกในเดือนเดียว"* และ "จากตะวันตก" คือสิ่งเดียวที่ไม่อยู่บนจอ

**แก้:** เพิ่มกอง `tails` ในลูปเดียวกัน รายงานเป็น **คำเตือน ไม่ใช่ error**
(ฉากที่เล่าปลายทางล้วนและต้นทางอยู่นอกจอมีอยู่จริง — แต่ต้องเป็นการตัดสินใจ
ไม่ใช่ความบังเอิญ ตระกูลเดียวกับ `CAM_FLOOR`)

**บทเรียนที่ใช้ซ้ำได้:** ตัวตรวจที่คำนวณค่าไว้ครบแล้วแต่ *ไม่ได้เอาไปเทียบ*
คือจุดบอดที่เงียบที่สุด — เงียบกว่ากฎที่ไม่มีตัวตรวจเสียอีก เพราะมันมีตัวตรวจแล้ว
**ตรวจตัวตรวจด้วยการนับว่ามันเทียบค่าที่มันคำนวณครบทุกตัวไหม**
(ตระกูลเดียวกับ E12 `check_routes` ข้อ 8 พังเงียบ และ E13 `label` บน clash ไม่ถูกวาด)

### E16 · ท่าข้ามที่ไม่เปียก — และแม่น้ำที่ไม่ตามแม่น้ำ (2026-09-01)

**อาการ:** เจ้าของดูภาพบทที่ 10–11 แล้วบอกว่า *"ถนนดูจะใช้เส้นตรงกันซะเยอะ ยิ่งที่
เจียนเย่ มันตรงเข้าไปได้เลยเหรอ"* · วัดแล้วพบว่า `jianye–shouchun` ประกาศ
`terrain:"ford"` มาตลอด แต่เส้นที่วาด **เปียก 0 หน่วย** — มันพาดข้ามแม่น้ำที่กว้าง
ที่สุดในแผ่นดินโดยเลี่ยงร่องน้ำไปพอดี · และ edge ที่ประกาศเป็น `river` ทั้งหกเส้น
เปียกแค่ 16–38% โดยมีช่วงแห้งติดต่อกันถึง **250 หน่วย**

**สาเหตุ:** ลาก `d` **ด้วยตาจากภาพครอปแผนที่** แทนที่จะอ่าน `landmask`
ถนนบทที่ 1–9 ไม่เป็นแบบนี้เพราะถูกลากสะสมมาหลายเซสชันโดยเทียบของจริง —
**ความต่างระหว่างของที่ทำเร็วกับของที่ทำสะสม มองไม่ออกจากภาพ แต่วัดออกได้ทันที**

**ทำไมตัวตรวจไม่เห็น:** ข้อ 5 ของ `check_routes` จับเฉพาะเส้นที่เปียก **เกิน**
เพดาน 30 หน่วย (= ลุยข้ามทะเลสาบ) · เส้นที่ *ควรเปียกแต่ไม่เปียก* หลุดออกทาง
ตรงข้ามของกฎเดียวกันทั้งหมด · **กฎที่ตรวจได้ทางเดียว = กฎที่มีรูอยู่อีกทาง**

**แก้:**
1. `tools/trace_river.js` — Dijkstra บน landmask · เลิกลากด้วยตา
2. `check_routes` ข้อ 5.1 — **ท่าข้ามต้องเปียกจริง** (+ แม่น้ำใหญ่ที่ข้ามโดยไม่มีท่า)
3. ⚠ ต้องดูที่ **edge** ไม่ใช่ที่ **node** — node ที่เป็น ford แปลว่า "ตรงนี้มีท่า"
   ไม่ได้แปลว่าถนนทุกเส้นที่มาบรรจบต้องข้ามน้ำ (ลองแบบ node แล้วได้ false positive ทันที)

**บทเรียนที่ใช้ซ้ำได้:** กฎเชิงปริมาณเกือบทุกข้อมีสองด้าน — "เกินไป" กับ "ไม่ถึง"
เราเขียนด้านเดียวมาตลอดทั้งโปรเจกต์ (แม่น้ำที่แห้ง §E15 · ท่าข้ามที่ไม่เปียก §E16)
**เขียนกฎใหม่เมื่อไหร่ ให้ถามทันทีว่าด้านตรงข้ามของมันคืออะไร**

### E17 · ตารางสถานะในเอกสารเน่าเงียบกว่าโค้ด (2026-09-01)

**อาการ:** ในเซสชันเดียวเจอ **ข้ออ้างที่ค้างสามครั้ง** โดยไม่ได้ตั้งใจหา:
1. §15 + LOG จดว่า **โหมดสองเอกภพ "ยังไม่เขียน"** — ทั้งที่เสร็จตั้งแต่ ซ.11
   และใช้ไปแล้วสองฉาก (c7-13 · c9-11) · เจ้าของถามว่า "มันยังไงนะ" ผมไปเปิดโค้ดดู
   ก่อนตอบ จึงเจอ — **ถ้าตอบจากเอกสารจะตอบผิดเต็ม ๆ**
2. LOG จดว่า **ตัวตรวจข้ามฉาก (ก) ยังไม่ทำ** — ทั้งที่ `check_map` ข้อ 5 ทำอยู่
3. LOG จดว่า **`check_click` เป็นบั๊กในโปรดักต์** (ก่อนไล่จริง) — เป็นบั๊กใน probe

**สาเหตุร่วม:** ตารางสถานะเขียนตอน *วางแผน* แล้วไม่มีใครกลับมาแก้ตอน *ทำเสร็จ* ·
**และไม่มีตัวตรวจตัวไหนอ่านเอกสาร** — ข้อมูลกับโค้ดมีตัวตรวจเฝ้าเจ็ดตัว
ส่วนเอกสารมีศูนย์ · มันจึงเน่าเงียบกว่าทั้งสองอย่าง

**แก้:** แก้ทั้งสามที่แล้ว · **แต่ทางแก้เชิงระบบคือนิสัย ไม่ใช่เครื่องมือ:**
> **ก่อนตอบคำถามว่า "X ทำแล้วหรือยัง" ให้เปิดโค้ดดูเสมอ อย่าตอบจากตาราง**

**บทเรียนที่ใช้ซ้ำได้:** เอกสารในโปรเจกต์นี้มีสองชนิด — **บันทึกว่าเกิดอะไรขึ้น**
(LOG §5 · BUGS_SEEN) กับ **ตารางว่าตอนนี้เป็นยังไง** (§15 · ของค้าง · STORYBOARD)
ชนิดแรกไม่เน่าเพราะมันเล่าอดีต · **ชนิดที่สองเน่าทุกครั้งที่มีคนทำงานเสร็จแล้วไม่กลับมาแก้**
เวลาอ่านเอกสารเก่า ให้เชื่อชนิดแรก และ**ตรวจสอบชนิดที่สองกับของจริงเสมอ**

### E18 · หน้าเปิด "แว้บ" — ตัดสินใจตอน JS ทำงาน ทั้งที่ต้องตัดสินก่อนเบราว์เซอร์วาด (2026-09-02)

**อาการ:** เจ้าของทัก *"กดเข้าลิงก์มามันเด้งหน้า Intro เสร็จแล้วมันเปลี่ยนไปหน้าแรกในทันทีเลย"*

**ที่ทำให้หาช้า: ทดสอบในเครื่องแล้วไม่เจอ** — จับเวลา 4 วินาทีก็เห็นหน้าเปิดค้างอยู่ปกติ
เพราะ localhost โหลด 2.3 MB เร็วจนไม่ทันเห็นช่วงที่มันแว้บ

**สาเหตุ:** `#intro` อยู่ต้น `<body>` (บรรทัด 38) ส่วนสคริปต์กับข้อมูล **รวม 2.3 MB**
อยู่ท้าย `<body>` (บรรทัด 148–164) · ลำดับจริงที่เบราว์เซอร์ทำคือ
1. parse HTML + CSS → **วาดหน้าเปิดเต็มจอ**
2. โหลด/แปลสคริปต์ 2.3 MB
3. `setupIntro()` ถึงจะได้ลบมันออก

ผู้อ่านที่เคยดูหน้าเปิดแล้ว (`tk-intro=1`) หรือมาด้วยลิงก์ตรงถึงฉาก จึงเห็นหน้าเปิด
**แว้บขึ้นมาแล้วหายไปทุกครั้ง** — และบนโฮสต์จริงที่ช้ากว่า localhost มันนานพอจะรำคาญ

**แก้:** ย้ายการตัดสินใจไปไว้ใน `<script>` จิ๋วใน `<head>` ที่ทำงาน**ก่อน paint** —
อ่าน localStorage/hash/query แล้วติดคลาส `no-intro` บน `<html>` · CSS ซ่อนไว้ตั้งแต่แรก
· `setupIntro()` ยังเป็นตัวตัดสินจริงเหมือนเดิม และ**ถอดคลาสเองถ้าตัดสินใจว่าจะโชว์**
(จำเป็นสำหรับเคส hash ที่ชี้ฉากไม่มีอยู่จริง — สคริปต์ใน head เห็นแค่ว่า "มี hash"
แต่ตัดสินไม่ได้ว่ามันชี้ไปฉากที่มีจริงไหม)

**บทเรียนที่ใช้ซ้ำได้:**
> **อะไรที่ "ต้องไม่ถูกเห็น" ต้องถูกตัดสินก่อน paint ไม่ใช่ตอน JS พร้อม**
> และ **การทดสอบบน localhost ปิดบังบั๊กประเภทนี้ทั้งตระกูล** เพราะมันเร็วเกินกว่า
> จะเห็นช่วงกลาง · เวลาแก้เรื่องจังหวะการโหลด ให้ถามว่า "ถ้าเน็ตช้ากว่านี้สิบเท่า
> ผู้อ่านจะเห็นอะไรระหว่างนั้น" — ไม่ใช่ "รันแล้วดูเหมือนจะโอเค"
